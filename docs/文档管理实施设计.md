# 第一阶段文档管理实施设计

状态：待实现的实施方案；2026-11-04。本文细化[第一阶段详细设计](第一阶段详细设计.md)，不表示文档上传、存储或清理功能已经存在。先交付上传和列表；删除接口须等持久化清理及恢复机制完成后再开放。

## 1. 范围和约束

- 一个文档属于一个知识库；同一知识库允许同名文件。用户只能操作自己的活动知识库和其中的文档。
- 单次请求上传一个文件，允许 PDF、MD、DOC、DOCX，单个文件大于 0 且不超过 50 MiB（52,428,800 字节）。首期不解析、切片或向量化；`uploaded` 仅表示文件保存成功。
- 原文件保存在服务器本地持久化目录，数据库保存元数据和服务端生成的存储键；不暴露物理路径。当前 Docker Compose 只持久化 PostgreSQL，尚未配置文件持久化。
- 后续能力包括当前知识库和跨本人知识库的文件名搜索、PDF/MD 预览、Word 下载、文档及知识库删除。文件上传不等于 AI 内容已可检索。

## 2. 数据及状态

以详细设计中的 `documents` 和 `file_cleanup_tasks` 为目标创建 Prisma 模型及迁移。`documents` 记录知识库 ID、展示用原文件名、唯一随机存储键、小写扩展名、可空识别类型、文件字节数、状态和时间；对 `(knowledge_base_id, created_at)` 建索引。文件大小在数据库使用 `bigint`，API 返回十进制字符串。为稳定分页，查询按 `createdAt desc, id desc`。文件名最多 255 字符，保留为展示数据，不能用于构造文件路径；拒绝空名称、路径分隔符、控制字符或包含非法文件名字符的输入，具体字符与长度校验按应用支持平台落地。

文档状态：`uploaded` 表示可访问，`deleting` 表示已受理删除且普通列表、详情及下载不再返回。知识库为 `active` 才能上传和查询；`deleting` 禁止新上传。实际可用状态值应通过迁移 CHECK 或等效服务端约束保证，不能仅依赖前端。`RESTRICT` 外键防止绕过清理直接删除父记录。

清理任务与文档一对一，保存存储键快照、次数、最近错误、下次执行时间。若采用跨事务的租约认领，迁移还需增加 `lease_owner`（可空）和 `lease_expires_at`（可空）并为可认领任务建立索引；进程崩溃后租约到期可由其他工作者接管。最终迁移前应结合数据库查询方式确认字段及索引，详细设计同步更新。

## 3. 存储与配置

计划增加服务端配置 `DOCUMENT_STORAGE_ROOT`，启动时解析为绝对路径并确保可读写；根目录不放进静态公开目录，不提交真实上传文件。根目录下分 `tmp` 与 `objects`，由同一文件系统承载，以便临时文件到目标文件使用同文件系统的原子重命名；服务端随机生成不含路径分隔符的存储键，所有文件操作都校验目标在预期根目录内，并拒绝符号链接等路径逃逸。

本地直接运行 API 时在 `.env` 中设置可写持久目录；未来 API 容器化时显式挂载该目录为持久卷，临时和正式目录都位于该卷下。当前没有 API 容器和文件卷，具体部署路径不预设。设置目录权限、备份数据库与文件的策略需在部署时落实。

## 4. 上传契约与校验

`POST /knowledge-bases/:id/documents`，需 Bearer access token，`Content-Type: multipart/form-data`，字段名 `file`，一次一个文件；成功返回 201 和文档公开元数据，不返回存储键或物理路径。请求错误：无权限或知识库不存在统一 404，输入无效或空文件 400，超过限制 413，不支持或内容不匹配 415，未认证 401。除具体文件数据外，响应字段建议与列表一致，包括 `id`、`knowledgeBaseId`、`originalName`、`fileExtension`、`mediaType`、`sizeBytes`、`status` 和时间。

在 multipart 解析器设置文件数和单文件大小上限，同时计数实际接收的字节；代理或网关也需配置不小于业务限制的请求体上限（multipart 有额外开销），明确超限处理，避免应用收到前被代理以不一致方式拒绝。不把文件全部放入进程内存：流式写入临时文件，拒绝多文件、缺失字段、空文件和异常中断，及时清理部分文件。

文件名按兼容 multipart 中文文件名的明确解码规则处理，拒绝路径和控制字符；扩展名去除大小写差异并校验白名单。服务端依据内容辅助识别：PDF 检查签名及基本结构；DOC 验证 OLE 容器并检查 Word 内容；DOCX 验证 ZIP/OOXML 所需结构并限制解压条目数、体积和压缩比；MD 检查有效 UTF-8 和合理文本内容。客户端 MIME 仅作参考，签名检查不是对文件安全性的完整保证。DOC/DOCX 的具体解析库和检测失败策略在实现前选定并验证，禁止无界解压。

## 5. 上传与删除并发及崩溃恢复

文件系统和数据库不能共用事务。采用以下计划方案，实施时须验证数据库锁语义和超时处理：

1. 先鉴权并初查知识库，再把上传流写到随机临时文件，限制大小和时长并校验内容；该阶段不持有数据库行锁。
2. 在数据库事务中对该知识库行取得排他行锁，再检查 `owner_id` 和 `status = active`。删除知识库的入口使用同一行锁，并在持锁事务中改为 `deleting`。
3. 获锁且状态有效时，将已校验的临时文件重命名到对象目录，随后创建文档记录并提交事务。持锁期间只执行本地重命名和数据库操作，设置锁等待和事务超时，避免上传网络过程占锁。
4. 如果删除先获得锁并提交，上传重新检查时发现 `deleting`，不得创建记录并清理临时文件。如果上传先提交，删除随后扫描时能看到已提交文档。异常时尽力清理本次文件，不向客户端泄露路径。
5. 重命名后、数据库提交前进程崩溃可能产生无记录对象；临时上传也可能留下残片。后台定期对账，只处理超过安全宽限期、没有对应文档记录且不属于仍在进行操作的对象；设计必须结合最大操作时长、事务超时和存储时间戳避免误删在途文件。无法可靠判断时保留文件并记录告警。临时目录也按宽限期清理。

上述锁协议要求所有创建文档、删除知识库的路径一致遵守；仅在应用层先查一次状态无法解决并发。若重命名失败、提交失败或结果不确定，按实际状态记录错误并由对账补偿。客户端遇到网络中断不能据此判断服务端是否提交，当前不承诺上传幂等；后续如需自动重试，先设计幂等键或查询确认。

## 6. 查询、下载与预览

- `GET /knowledge-bases/:id/documents`：先验证知识库所有权及活动状态，再按 `q`、`type`、`page`、`pageSize` 查询 `uploaded` 文档；缺省 `page=1`、`pageSize=20`、最大 100，响应 `{ items, total, page, pageSize }`。`q` 上限 100，大小写不敏感子串匹配，`%`、`_` 按普通字符处理；扩展名筛选只接受白名单。
- `GET /documents/search`：必填 `q`，仅跨当前用户的活动知识库及 `uploaded` 文档查询，附所属知识库信息，分页同上。
- `GET /documents/:id` 与 `GET /documents/:id/content`：查询时连接知识库并限制所有权及状态；不存在和无权访问统一 404。文件流设置可信 `Content-Type`、安全的 `Content-Disposition` 和 `X-Content-Type-Options: nosniff`，防止路径或响应头注入。
- PDF 通过授权请求获得 Blob URL 供浏览器预览；MD 获取后以安全 Markdown 渲染并清理不可信 HTML；DOC/DOCX 首期下载。前端关闭或替换预览时释放 Blob URL。Blob 方式会占浏览器内存；大文件流式或分段预览留待单独设计。

## 7. 删除及恢复

删除文档时，事务内将文档改为 `deleting` 并以文档 ID 唯一约束创建清理任务；重复请求不得生成重复任务。API 返回 202，表示受理而非文件已删除。后台工作者原子认领到期任务并设置租约；删除文件时，文件不存在视为成功。成功后在一个事务中删除清理任务和文档记录；失败记录安全错误信息，增加次数，按退避策略安排重试。记录不暴露存储路径给用户。

删除知识库时，与上传共用知识库行锁，在事务内标记 `deleting`。恢复扫描器分批为尚未进入清理流程的文档创建任务，任务完成后检查无剩余文档，再删除知识库；扫描可在进程中断后继续。并发工作者使用行锁或到期租约避免同一任务同时被处理；需要限制批量大小和定时扫描频率，并记录失败与告警。

详细重试次数、退避上限、租约时长、对账间隔和存储容量阈值属于实现配置，编码前确定并验证；不能默默丢弃长期失败任务。用户删除和文件备份恢复不在本阶段实现，但部署时需要明确备份一致性。

## 8. 开发顺序和验收

1. 创建文档模型及迁移，确认约束、索引和已有数据安全；建立持久化存储配置。
2. 实现流式上传、校验、上锁协议、失败清理及上传孤儿对账；实现受权限保护的列表。先以手动操作验证再接前端。
3. 接入前端选择、上传进度与列表；上传成功展示“已上传”，不能展示成已解析。明确重复提交与网络失败提示。
4. 接入详情、授权下载、PDF/MD 预览和文件名搜索。
5. 实现清理任务、租约、重试和知识库删除恢复扫描；验证失败恢复后再开放删除接口与按钮。
6. 检查两个账号的权限、上传与删除并发、文件超限与伪造类型、崩溃后孤儿对账、删除失败重试及服务重启后的持久化。以上属于验收目标，不表示当前已经完成。

本阶段不安排 AI 解析或跨标签页认证重构；多标签页认证仍是已知限制，不能视为已经解决。
